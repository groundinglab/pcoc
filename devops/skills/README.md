# Portable execution recipes — reference WIP

These **seven newly written portable reference recipes** are task guidance, not installed bot skills, adopted policy or validated automation. They retain the operational method without copying uncleared private source bodies. All ten discovered workflow sources are reconciled in [the source inventory](../sources/README.md), including duplicate lineage and deliberate omissions. Source-present, shared-installed, attached-to-a-bot and proven invocation are different facts. **Per-bot attachment is UNKNOWN.**

Use the task owner's one policy reference for permission, severity, caps and stop rules. Each recipe takes a task/pin, approved scope/environment and evidence destination. Nothing here authorises a login, test, contact, merge or deployment. No all-skills installation is required; follow these as plain instructions manually or provide them to your own AI.

## Intent-backed acceptance

Before implementation, identify the output and pin the contract. For each criterion write Must, Why and an optional Push-back, then an exact observable check and deliberate negative. Report ambiguity rather than inventing rules. Return the locked criteria and evidence locations, not just a reassuring summary.

## Local build and repair

Use the owner’s approved builder and environment; a manual developer is equally valid. Preserve unrelated work, verify dependencies and legitimate access, record base/prompt/settings, and confirm a real session if using a builder. Run the project checks; record command output and code revision. Diagnose case/inputs before retrying within existing limits. Stop on the governing signature/budget rule. Return artifact, head and actual evidence; build permission is not publish permission.

## Adversarial review

At the pinned head, attack the intended property and weak criteria: seek bypasses, cheaper shortcuts and dishonest passes beyond existing happy-path tests. Give exact location, mechanism, impact, evidence and a confirm/falsify procedure. Separate source-demonstrated flaws from untested hypotheses. Test only in an authorised environment. Use the governing severity vocabulary before budget. Return an independent verdict; do not wait for reviewer consensus.

## Defensive review

At the pinned head, check implementation against the contract and audit the builder’s evidence. Verify that required tests ran at that head, assertions can fail, expected values are independent where required and negatives fail for the intended reason. Treat missing or wrong-revision proof according to existing severity. Assess supplied adversarial findings on evidence without a consensus loop. Return coverage, findings, limitations and revision binding; clearance is not deployment approval.

## Lab/run planning

Separate stable project preferences from changing run variables. Resolve purpose, machine class, pin, allowed inputs, clock/source actual versus target where relevant and excluded work. Do not use a virtual-machine smoke time as a bare-metal acceptance measurement. Copy approved specifications exactly; stop on consequential ambiguity. Keep project clock values, host names and builder settings in the owner’s run record, not this portable method. This recipe does not authorise a lab run.

## Project oversight

Review only the named project and owner-supplied status/evidence. Compare recent changes, CI and documentation against locked requirements; identify unowned work, stale claims and terminology drift. Return only actionable misses with precise locations and a suggested owner. Contact others or create recurring monitors only if separately authorised. Oversight is optional, not a permanent per-ticket overseer.

## Website release

Read the current project runbook; identify source/base, target and rollback before release. Run each relevant check on base and candidate and classify introduced versus baseline failures without weakening gates. Build a staging copy without secrets; keep preview transformations and data bindings separate. Inspect routes, links and wide/narrow layouts. Publish only under existing permission and required release checks. Verify live source/build/deployment identity and rollback; report unavailable checks and never claim speed gains without a measured comparator.

## Proposed ticket-stamping method — not installed or validated

A separate pre-build recipe has been proposed, not adopted: identify the submitted artifact/hash, authoritative policy/playbook identity and head; compare self-check claims with mechanical checks; separately judge ambiguity, intent and evidence. Return one consolidated findings response per submission, state any stamp's exact artifact/identity/scope, and do not invent authority when a critical input is missing (S0/blocking ambiguity in the governing vocabulary). Promote proven repeatable checks into the existing script only through its normal change process. Speed improvement is a hypothesis, not measured here. Project check IDs and policy values belong in the runbook, not the generic recipe. This paragraph neither stamps anything nor adds a gate.

## Use evidence, not availability

The internal adversarial and defensive recipes received own/cross-review of their wording; this is not completed review of the unfinished producer. A website-release recipe was reported used for one real deployment; no earlier measured comparator established a speed-up. This public rewrite has not been independently exercised end to end. Lab planning and oversight use remain unverified in the selected evidence. Do not infer attachment or invocation from a skill name in a catalog.
