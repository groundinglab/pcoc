# Rule I6 / hike-shortcut check, round 1 (read only, nothing changed)

Rule I6 (SPEC L2130–2132) and §11.1 L830: every step loads all `SLOT_BYTES` of the selected slot and mixes every word with `S`. No cache, table, summary or partial read is allowed in the terrain, leg, step or fold.

## B1: Sonnet TypeScript, hand-written WASM kernel (`impl/src/wasm.ts`, used by `impl/src/core.ts`)
- **Leg kernel `legBody()` (wasm.ts L91–113):** every step computes `p = (S mod nSlots) · slotBytes` and `end = p + slotBytes`, resets `acc = 0`, then loops `acc += mix64(load64(p) XOR S)` with `p += 8` while `p < end`. That is every 8-byte word of the slot (`SLOT_BYTES` is a multiple of 8). Then `S = seal(acc)`, which calls back into JS (`createHash('sha256')` over `pcoc-walk-v1 ‖ le64(acc)`). `mix64` (L51–58) includes `+MIX_ADD` and both multiplies.
  - No per-slot state survives a step. Nothing is stored except `acc` and `S`. There is no table and no early exit.
- **Fill kernel `fillSlotBody()` (L60–89):** per word it computes NL4 (the four lanes, read from a lane copy placed after the terrain), the three parents in order with `rotl(pw, j+k)` and `k·PARENT_MUL`, then `slot_mix`. Slot 0 is called with `hasParents = 0`, so it gets no parents and no mix (§10.4 L766). Terrain is filled once per `Terrain` (once per verify, verify.ts L255) and never shared across keys.
- **Correctness evidence:** B1's kernel results equal B2's independent numpy results on every terrain digest (S1, S2, PROD), every leg, and the fold trace. B1's BigInt reference `stepRef` (core.ts L160–167) produces the fold trace, which also matches.
- **Caches seen:**
  - `kernel ??= new WebAssembly.Module(...)` (core.ts L111) caches compiled code, not hike data.
  - `readCache` (verify.ts L133) caches header-index reads, not hike data.
  - The `cached_leg` Map exists only in `negatives.ts`, which only the generator imports (gen/candidates.ts L7).
  - None of these is an I6 issue.
- **Flag under the speed-up rule:** the kernel exists to make the fill and fold faster than a BigInt loop: about 8.3 s per production leg (B1's own report), and B1 verified O3 at PROD (fill plus 6 legs) in 60 s on the box. It does **not** reduce work, since each step still loads and mixes the full slot. It is native-integer speed, not a shortcut. Christian's rule says any producer speed-up is flagged, so here is the flag: **no I6 violation found, speed-up noted, adversarial check still recommended.** An independent full-slot reference (B2) agrees on every leg, which is the strongest available check that no bytes are skipped.
- **Minor:** SHA-256 runs through Node's OpenSSL, which uses SHA-NI or Armv8 SHA2 where present (§11.1 L836). Each step crosses the WASM→JS boundary for the seal. That costs speed only, not correctness.

## B2: Sol Python, numpy (`impl/core.py`)
- **`step()` (core.py L138–146):** `slot = t[i*wps:(i+1)*wps]` (the complete slot every call), `mixed = _mix64v(slot ^ S)`, `acc = np.add.reduce(mixed, dtype=uint64)`. That is a wrapping sum over all `WORDS_PER_SLOT` words, followed by the SHA-256 seal. `_mix64v` (L80–85) includes `+MIX_ADD`. Nothing is cached between steps.
- **`terrain()` (L111–131):** filled once per call (once per verify, verify.py L81). It uses the full NL4, three parents and `slot_mix`, and slot 0 is unmixed.
- **Concerns:**
  - No I6 violation in the construction path.
  - Its `negatives.py` (generator only) is wrong in the other direction. It fails to compute several shortcuts at all (see DIFF C5), so it doesn't prove those negatives are rejected.
  - Speed: numpy vectorisation of the full-slot fold is native-array speed, not a work reduction. O3 verify took 267 s on the box.

## Verdict
- **No I6 violation in either build.** Both read and mix the full slot every step, with no cache, table or partial read on any construction path.
- **Flag (B1):** the hand-written WASM kernel is a speed-up by implementation, not a shortcut. It should still get adversarial review against the permanent negatives before anything from it is reused.
- **Concern (B2):** its permanent-negative generator is defective. It has placeholders, honest values reported as negatives, and a hard-coded `matches_honest = false`. So B2 doesn't actually demonstrate rejecting `cached_leg`, `partial_slot_read_2047`, `one_lane_flip`, `all4_kernel`, `f3_shared_terrain` or `squeezed_seed_terrain`.
