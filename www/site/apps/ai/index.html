Apps

Point a coding agent at the specification

The specification is precise enough that an independent implementation can measure the same object as everyone else. Give it, and your own code, to a coding agent. The agent does the wiring. You read the diff.

This is not an app, and it is not a download.

What this is

A PCOC is an identifier the maker's own device creates. It carries a cost in memory and time, so a new one is not free. Checking that cost is cheap, and the check does not decide who gets in. That decision is the service's policy.

The specification is the contract between implementations. The SDKs (Rust, C, Go, and Java) are a tested shortcut when the language matches. They are not required. Building straight from the specification is fine when they do not fit, as long as the objects still measure the same way.

The website copy of the specification is the tagged 2.3 file. The repository guide splits that same version into six documents and says which ones to open. The prompt tells the agent to start there, and to stop if the two disagree.

What you can ask it to do

  • On the maker's device: create the key, hold the memory, and produce the object.
  • On a service: measure the object, then apply your policy. The measurement and the policy stay separate.
  • Both.

For a service, the sign-in can sit beside email or the sign-in you already offer. The words for that button are "Continue with PCOC". It is another way in, not an account at a third party. For an app, a settings control can say "Create a PCOC to secure this account".

A service can take the sign-in quietly and finish the slow check in the background, so an honest person is not left waiting on a one-word screen. The prompt says how. You still choose the policy numbers. The specification does not set them, and it does not set a deadline for how soon the object must be shown.

The prompt

Paste this into the agent. You can hand it this whole page instead, and tell it to follow the prompt.

You are integrating PCOC into this codebase. Make the smallest change that
adds the capability the human names. If they did not name a side, ask before
you edit: a producer, a verifier plus an admission gate, or both.

PCOC means production-constrained observable commitment. It is a self-issued
identifier. The maker's device creates the key and holds memory while
Bitcoin blocks pass. Anyone can measure that cost. The measurement does not
decide who gets in. Admission policy does, afterwards.

The specification is the interoperability contract. An implementation built
only from it must produce objects that another implementation of the same
specification can measure, and must measure the production profile's held
cost correctly: 256 MiB of memory (TERRAIN_BYTES = 268435456) across 18
stages, paced by Bitcoin block headers. The wire kind stays
v2.2-pcoc-object. The specification version is 2.3, tag spec-2.3.0. That is
not an SDK package version (2.3.x).

Do this:

1. Read the specification before you write code.
   Clone https://github.com/groundinglab/pcoc as a full clone. A shallow
   clone has no tags, and the pin check needs them.
   On current main the specification is six documents. Start at
   spec/README.md and spec/GUIDE.md.
   Producer: spec/01-Satoshi_Hike_Construction.md,
   spec/05-Conformance_Process.md, spec/02-Producer_Process.md,
   spec/03-Waypoint_Publication_Process.md when planting through that
   channel, and only section 14.3 of spec/06-Measurement_Record_Process.md
   for the path-body check.
   Verifier: Construction, Conformance,
   spec/06-Measurement_Record_Process.md, and Waypoint Publication only to
   interpret that channel's evidence.
   Admission gate: the verifier documents, plus
   spec/04-Admission_Process.md, plus the policy file the human names.
   Policy values are not part of the specification.
   A readable copy of the tagged single file is
   https://groundinglab.io/technical/spec/ (tag spec-2.3.0, commit 7189a6d,
   path spec/satoshi-hike-v2.3/SPEC.md). Same specification version. If the
   six documents and that page disagree, stop and report the disagreement.
   Do not invent a third rule.
   Do not add fields, encodings, kinds, or rules the specification does not
   define.

2. Prefer a published SDK when the language matches.
   Rust, C, Go, and Java are tested against one conformance pack. Where an
   SDK and the specification disagree, the specification wins.
   Use the tag that git rev-parse can see. As of this page: Rust
   sdk-rust-v2.3.1, Go sdk/go/v2.3.1, C sdk-c-v2.3.1, Java sdk-java-v2.3.1.
   Quickstarts are on https://groundinglab.io/technical/sdk/ and in each
   language README under sdk/. The public SDK page's GitHub release list
   still shows C and Java at 2.3.0. Prefer the 2.3.1 tag when it exists in
   the clone.
   Rust, from sdk/rust: cargo run -p pcoc-cli --release --quiet --
   quickstart
   C, from sdk/c: make -j4 build/pcoc && ./build/pcoc quickstart
   Go, from sdk/go: go run ./cmd/pcoc quickstart
   Java, from sdk/java: ./gradlew run --args=quickstart
   Implement directly from the specification only when no suitable SDK
   exists. After a direct implementation, run the conformance checks in step
   7.

3. Keep these boundaries.
   Produce and measure do not judge. Accept, refuse, and revoke are
   admission policy, after measurement. The measurement record does not say
   pass or fail.
   Signature checks belong to admission, not to produce or measure
   (Construction rule P2.2).
   The specification defines no tip-versus-last-beacon submit deadline. Do
   not add submission_deadline_blocks, and do not add a lever named K. Do
   not bring that deadline back from an older web page.
   Do not enable sticky refuse. It is not required. The in-repo groundinglab
   policy sets sticky_refuse = false, off for testing. Leave it off unless
   the human's own policy file sets it.
   Bitcoin is the clock and the timestamp. Optional waypoint batching is
   Bari (spec/03-Waypoint_Publication_Process.md). Do not add another
   external service for the core construction. Hosted Bari, the index, and
   the gate are optional. Do not require a signup to a bot-protection
   vendor.
   Surface every policy lever for a human to set. Do not hard-code a
   threshold the specification leaves to policy. Read policy/README.md and
   the policy file the human chooses. groundinglab's in-repo successor is
   policy/groundinglab-admission/gl-admit-v12.toml. It is not necessarily
   what the live host is running. Do not copy its numbers into the
   specification, and do not treat them as required for someone else's gate.

4. When you touch product UI, write for the person using it. Keep
specification words out of that copy.
   A service sign-in option, beside email or whatever sign-in the product
   already has: "Continue with PCOC". It is another way in. It is not an
   account at a third party.
   An app control that makes one: "Create a PCOC to secure this account".
   Say what happened in a sentence. The sign-in client sentences are
   "Sign-in submitted", "bad signature", and "malformed". Do not leave the
   person on a stuck one-word state.
   Silent submit, then the slow check in the background: POST /v1/sign-in
   returns after the fast checks, body {"delivery":"ok"}, and does not wait
   for the thorough check. Treat that response, and a provisional grant that
   has not settled, as signed in immediately. The result token stays pending
   until the thorough check settles. See services/admission-gate/WIRE.md and
   spec/04-Admission_Process.md section 15.3. This is the service's own UX.
   It is not a new field on the object.

5. Devices.
   Making one holds about 256 MiB for the whole hike: 18 Bitcoin blocks,
   typically around three hours or more, and it varies. The device has to
   stay awake and keep that memory. A laptop that can spare it is a good
   fit. The published demonstrators are the Linux desktop app and the
   Android phone app.
   A phone can run the demonstrator. Produce is a poor fit where the OS
   sleeps the app, kills it in the background, or cannot keep 256 MiB free.
   Checking one does not hold that memory. It redoes a sample and reads
   Bitcoin's public record, or an index.
   The specification's low-end host for measuring a leg-rate floor is an
   Intel Core i7-10610U laptop. That is a calibration host, not a list of
   allowed devices.

6. Security.
   Flag any change that touches key material, signatures, or path
   validation, and wait for the human to confirm it.
   Do not log or commit private keys. Demo keys in the tree are not a seed
   for a real object.

7. Show that it is done.
   Producer: an object a verifier that followed the specification can
   measure, including a verifier that is not your code, plus the conformance
   result.
   Verifier: a measurement record of the held cost in the section 14 shape,
   with no accept or refuse inside that record.
   Gate: policy levers in a file a human can edit, separate from
   measurement. Show where each value is set.
   Conformance, from a full clone: python3
   spec/conformance/tools/ring1_checks.py and the language quickstart in
   step 2. The pack manifest SHA-256 is
   91ded57e5c05b7cb4cd74d313a51d83d2373fa86dc625df41faed9586e9032af,
   recorded in sdk/SPEC_PIN beside tag spec-2.3.0. The pack is
   spec/conformance/pack. Its manifest id pack-2.2.0 is a historical name.
   The bytes are valid for specification 2.3.
   Examples: https://groundinglab.io/technical/integrate-a-producer/ ,
   apps/desktop , and https://github.com/groundinglab/primal-pcoc for a
   producer. https://groundinglab.io/technical/verifier-and-policy/ and the
   SDK verify commands for a verifier.
   https://groundinglab.io/technical/integrate-an-admission-gate/ ,
   https://groundinglab.io/technical/sign-in-wire/ , and
   services/admission-gate for a gate. If the verifier-and-policy page's
   worked policy numbers disagree with policy/README.md, follow
   policy/README.md.

Start by reading spec/GUIDE.md and the SDK or example for this repository's
language. Then propose the smallest change. Do not refactor unrelated code.

What you do

  1. Open your repository in the agent, or tell it the path.
  2. Say which side you want, and the language if you know it.
  3. Paste the prompt.
  4. Read the diff before you keep it. Stop on keys, signatures, and anything that decides who gets in. You set those numbers.
  5. Run the conformance command the agent shows you. The quickstart lines are on the SDK page.

Where it should read

  • The specification, and in the repository spec/GUIDE.md plus Satoshi Hike Construction.
  • SDKs, with quickstarts and the tags that are cut.
  • Integrate a producer, Verifier and policy, Integrate an admission gate, and the sign-in wire.
  • The conformance pack, spec/conformance/pack. The manifest SHA-256 is in sdk/SPEC_PIN.
  • Worked code: the desktop app, the Android demonstrator, and the admission gate. Policy levers live in policy/README.md, not in the specification.

What done looks like

A producer is done when an object it makes is measured by a verifier that followed the specification, including one that did not use your code.

A verifier is done when its record matches the reference shape and the conformance pack, and the record itself does not admit or refuse anyone.

A gate is done when that measurement stays separate from the policy file, and a person can see and change every lever. Show the conformance result, or the exact command that produces it.

Devices

Making one holds about 256 MiB the whole time. It takes 18 Bitcoin blocks, typically around three hours or more, and it varies. Leave the device running. A laptop that can spare that memory is the straightforward fit. The Linux and Android apps are the demonstrators.

A phone can make one. It is a poor fit when the system sleeps the app, kills it in the background, or cannot keep 256 MiB free. Checking one is the cheap part. It does not hold that memory.

The specification names a low-end laptop only as the machine used to measure a rate floor. That is not a list of allowed devices.
